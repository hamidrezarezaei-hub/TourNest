## ۱. مقدمه

### ۱.۱ هدف سند

این سند چشم‌انداز، دامنه و ذی‌نفعان پروژهٔ **TourNest** را تعریف می‌کند.

هدف آن ایجاد درکی مشترک میان تیم توسعه و ذی‌نفعان دربارهٔ این موضوع است که «چه چیزی می‌سازیم، برای چه کسی و چرا».

این سند قرارداد رسمی نیست، بلکه مرجعی برای تصمیم‌گیری‌های بعدی در طول توسعهٔ پروژه است و در صورت نیاز بازبینی می‌شود.

### ۱.۲ دامنهٔ سند

- **در دامنه:** اهداف پروژه، کاربران هدف، محدودهٔ محصول اولیه (MVP)، معیارهای موفقیت و ریسک‌های سطح بالا.
- **خارج از دامنه:** جزئیات فنی پیاده‌سازی، طراحی دقیق رابط کاربری و نیازمندی‌های عملکردی تفصیلی که در مستندات مربوط به نیازمندی‌ها بررسی می‌شوند.

### ۱.۳ تعاریف و اصطلاحات

| اصطلاح | تعریف |
|--------|--------|
| **MVP** | Minimum Viable Product — کمینهٔ محصول قابل ارائه |
| **User Story** | توصیف یک نیازمندی از دیدگاه کاربر |
| **Persona** | نمایندهٔ فرضی یکی از گروه‌های کاربران هدف |
| **Sprint** | بازهٔ زمانی مشخص برای انجام بخشی از توسعه |
| **DoD** | Definition of Done — معیارهای تکمیل یک کار |

### ۱.۴ مراجع
- IEEE 830 — Recommended Practice for Software Requirements Specifications
- Roman Pichler — Product Vision Board

## ۲. چشم‌انداز محصول

### ۲.۱ بیانیهٔ چشم‌انداز (Vision Statement)

> **برای** گردشگرانی که برای یافتن تور مناسب با پراکندگی اطلاعات و دشواری پیگیری جزئیات مواجه‌اند و راهنمایان توری که درخواست‌های مشتریان را مدیریت می‌کنند،
>
> **TourNest** یک **سامانهٔ تحت وب معرفی تورهای گردشگری و مدیریت درخواست‌های رزرو** است
>
> **که** مشاهدهٔ اطلاعات تورها، ثبت درخواست رزرو و بررسی وضعیت درخواست‌ها را ساده‌تر می‌کند.
>
> **برخلاف** روش‌هایی که اطلاعات تورها و درخواست‌های مشتریان در پست‌ها، استوری‌ها و پیام‌های پراکنده قرار دارند، محصول ما اطلاعات تورها و فرایند درخواست رزرو را در یک سامانهٔ متمرکز ارائه می‌دهد.

### ۲.۲ ارزش پیشنهادی (Value Proposition)

| برای | ارزش |
|------|-------|
| **گردشگر** | مشاهدهٔ متمرکز اطلاعات تورها، بررسی جزئیات و ثبت درخواست رزرو |
| **راهنمای تور** | معرفی و مدیریت تورها، مشاهدهٔ درخواست‌ها و تأیید یا رد آن‌ها |
| **مسئول هماهنگی** | دسترسی به اطلاعات تورها و درخواست‌ها و پیگیری هماهنگی‌های مرتبط |
| **تیم توسعه** | طراحی و پیاده‌سازی یک سامانهٔ کاربردی با رعایت اصول تحلیل و طراحی نرم‌افزار |

### ۲.۳ مزیت رقابتی

- **تمرکز:** ارائهٔ اطلاعات تورهای گردشگری در یک سامانهٔ مشخص.
- **دسترسی آسان:** امکان مشاهدهٔ جزئیات تور بدون نیاز به پرس‌وجوی مکرر از راهنما.
- **شفافیت:** نمایش اطلاعات مهم تور پیش از ثبت درخواست رزرو.
- **پیگیری:** ثبت درخواست‌ها و امکان بررسی وضعیت آن‌ها توسط افراد مسئول.

## ۳. مشکل و فرصت

### ۳.۱ مشکل فعلی (Problem Statement)

راهنمایان تور که عمدتاً از شبکه‌های اجتماعی برای معرفی تورهای خود استفاده می‌کنند و گردشگران آن‌ها با چالش‌های زیر مواجه‌اند:

1. **پراکندگی اطلاعات:** اطلاعات تورها در پست‌ها، استوری‌ها و پیام‌های مختلف قرار دارد.
2. **دشواری دسترسی:** گردشگر برای اطلاع از جزئیات تور ممکن است مجبور به ارسال پیام و انتظار برای پاسخ باشد.
3. **دشواری مقایسه:** بررسی و مقایسهٔ تورهای مختلف به دلیل پراکندگی اطلاعات ساده نیست.
4. **پرسش‌های تکراری:** راهنما مجبور است اطلاعات مشابهی را بارها برای مشتریان توضیح دهد.
5. **پیگیری درخواست‌ها:** مدیریت و پیگیری درخواست‌های رزرو در پیام‌های پراکنده می‌تواند دشوار باشد.

### ۳.۲ فرصت (Opportunity)

- فراهم کردن دسترسی متمرکز به اطلاعات تورهای گردشگری.
- ساده‌تر کردن فرایند انتخاب تور برای گردشگران.
- کاهش وابستگی به پیام‌های پراکنده برای ثبت و پیگیری درخواست‌ها.
- ایجاد بستری برای مدیریت منظم‌تر تورها و درخواست‌های رزرو.

## ۵. محدودهٔ محصول

### ۵.۱ داخل محدوده (In Scope — MVP)

**کاربری (Functional):**

- **F-01** نمایش فهرست تورهای گردشگری.
- **F-02** نمایش جزئیات هر تور، شامل اطلاعاتی مانند مقصد، زمان، هزینه و برنامهٔ سفر.
- **F-03** ثبت درخواست رزرو توسط گردشگر.
- **F-04** بررسی درخواست رزرو و تأیید یا رد آن توسط راهنمای تور.
- **F-05** مشاهده و پیگیری درخواست‌های رزرو توسط کاربران مسئول.
- **F-06** پنل مدیریت تورها برای افزودن، ویرایش و حذف اطلاعات تور.
- **F-07** نمایش وضعیت درخواست رزرو به گردشگر.

**غیرکاربری (Non-functional):**

- **NF-01** رابط کاربری ساده و قابل‌فهم برای کاربران.
- **NF-02** پشتیبانی از نمایش مناسب در موبایل و رایانه.
- **NF-03** نگهداری امن اطلاعات حساب‌های کاربری و گذرواژه‌ها.
- **NF-04** اعتبارسنجی اطلاعات واردشده در فرم‌ها.
- **NF-05** پشتیبانی از زبان فارسی و چیدمان راست‌به‌چپ (RTL).

### ۵.۲ خارج از محدوده (Out of Scope)

| مورد | دلیل |
|------|-------|
| پرداخت آنلاین واقعی | افزایش پیچیدگی و نیاز به زیرساخت پرداخت |
| اپلیکیشن مستقل موبایل | تمرکز پروژه بر سامانهٔ تحت وب |
| سامانهٔ حمل‌ونقل گردشگران | خارج از نیازهای اصلی پروژه |
| چت آنلاین پشتیبانی | برای عملکرد اصلی سامانه ضروری نیست |
| سیستم امتیازدهی و نظرات کاربران | در محدودهٔ اولیهٔ پروژه قرار ندارد |
| چندزبانه بودن سامانه | تمرکز نسخهٔ اولیه بر زبان فارسی |

### ۵.۳ محدودیت‌ها (Constraints)
- زمانی: ۱۴ هفته، ۳ Sprint
- تیمی: ۳ نفر
- فنی: بدون سرور اختصاصی، استقرار روی سرویس ابری رایگان
- بودجه: صفر (فقط ابزارهای رایگان).

## ۸. رویکرد و متدولوژی

### ۸.۱ متدولوژی

- **رویکرد توسعه:** توسعهٔ مرحله‌ای و تقسیم کار میان اعضای تیم.
- **ابزار مدیریت و همکاری:** GitHub.
- **مستندسازی:** فایل‌های Markdown در مخزن GitHub.
- **بازبینی:** بررسی پیشرفت کار و هماهنگی اعضای تیم در طول توسعه.

### ۸.۲ فناوری پیشنهادی

| لایه | فناوری |
|------|--------|
| Backend | Django |
| Frontend | HTML، CSS و JavaScript |
| Database | پایگاه دادهٔ سازگار با Django؛ انتخاب نهایی متناسب با نیاز پروژه |
| Version Control | Git و GitHub |
| مستندسازی | Markdown در GitHub |

### ۸.۳ Definition of Done

یک قابلیت زمانی تکمیل‌شده محسوب می‌شود که:

1. پیاده‌سازی آن انجام شده باشد.
2. عملکرد آن بررسی و آزمایش شده باشد.
3. خطاهای مهم شناسایی‌شده برطرف شده باشند.
4. تغییرات مربوطه در مخزن پروژه ثبت شده باشند.
5. در صورت نیاز، مستندات مرتبط به‌روزرسانی شده باشند.
